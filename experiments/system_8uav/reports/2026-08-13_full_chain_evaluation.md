# 8 无人机 Gazebo 全链路仿真评估报告

## 1. 结论

当前提交 `e550e15feecc9b183ae373de9a3e7a6522c011f3` **尚不具备无人值守全链路运行条件**。

本次从英文自然语言入口发起了 4 条任务，覆盖单圆形、顺序“直线→圆形”和并行分组后合并。4 条指令共触发 12 次 LLM 调用，均在 JSON 解码阶段失败，因此严格意义上的“英文自然语言→队形完成”成功次数为 **0**。

为了定位阻断层，使用同一任务的已验证 Candidate LFS 继续驱动真实的 8 机 Gazebo/PX4 栈。结果证明：状态快照、几何分配、命令发布、PX4 位置控制和完成反馈能够工作；在 `px4_position` 对照模式下完成了 2 次连续队形变换。默认 `ladrc_acceleration` 路径的两次冷启动圆形任务均超时，失败规模分别为 8/8 和 3/8，可靠性不足。

综合判断：框架骨架可用，但 LLM 输出清洗、飞控启动握手、LADRC 加速度闭环和完成门限仍有阻断性问题。

## 2. 测试范围与环境

- 日期：2026-08-13，Asia/Shanghai
- 代码：`main`，提交 `e550e15f`
- 仿真：Gazebo Classic 11.10.2，PX4 SITL，8 个 iris 实例，lockstep，速度因子 1
- 通信：Micro XRCE-DDS Agent UDP/8888，ROS 2 Humble
- 调度策略：`paper-current-v2`，`safety_aware`
- 默认控制：`ladrc_acceleration`
- 对照控制：`px4_position`
- 圆形目标：中心 `[0, 13.5, 5] m`，半径 `4 m`，期望时长 `12 s`
- 直线目标：中心 `[0, 13.5, 5] m`，相邻间距 `3 m`，期望时长 `12 s`

所有仿真均实际启动 8 个 PX4 实例、8 个控制节点和 Gazebo；测试结束后相关进程已清理。

## 3. 英文自然语言入口测试

### 3.1 指令集

1. 单阶段圆形：`Have UAVs 1 through 8 form a circle ...`
2. 同义简化圆形：`Form a circle with UAVs 1, 2, ... and 8 ...`
3. 顺序任务：`First form a horizontal line ... After stable hover, form a circle ...`
4. 并行后合并：`First, make UAVs 1 through 4 ... and UAVs 5 through 8 ... simultaneously ... Then merge ...`

### 3.2 结果

| 指令 | LLM 尝试 | 累计调用耗时 | 有效 JSON | 结果 |
|---|---:|---:|---:|---|
| 单圆形 | 3 | 31.50 s | 0 | `JSONDecodeError` |
| 简化单圆形 | 3 | 42.72 s | 0 | `JSONDecodeError` |
| 顺序直线→圆形 | 3 | 105.51 s | 0 | `JSONDecodeError` |
| 并行分组→合并 | 3 | 101.06 s | 0 | `JSONDecodeError` |
| 合计 | 12 | 280.80 s | 0 | 全部阻断于解析层 |

单次 LLM 调用平均 23.40 s。失败类型包括 `Extra data`、`Expecting value` 和 `Expecting property name enclosed in double quotes`。

额外抓取一次模型原始响应后确认：提供方在 `response_format=json_object` 下仍返回 `<think>...</think>`，思考文本内含多个 JSON 片段，末尾才是最终 JSON。当前清洗函数使用跨全文的贪婪正则 `\{.*\}`，会从思考文本里的第一个左花括号截取到最终对象的最后一个右花括号，必然可能产生 `Extra data`。解析器的 3 次重试没有改变提示或清洗策略，因此重复付费和等待，但无法恢复。

## 4. 真实 8 机仿真结果

由于自然语言入口全部阻断，以下隔离测试直接注入由相同英文任务对应的、通过项目 schema 校验的 Candidate LFS。它们不计作全链路成功，但可用于定位后续层是否正常。

| 试次 | 冷启动 | 控制模式 | 任务 | 完成门限 | 结果 |
|---|---|---|---|---:|---|
| S1 | 是 | `ladrc_acceleration` | 8 机圆形 | 120 s | 失败，8/8 未稳定 |
| S2 | 是 | `px4_position` | 8 机圆形 | 45 s | 门限超时，UAV1/2/8 未稳定；约 3 s 后 8/8 稳定 |
| S3 | 否，承接 S2 | `px4_position` | 圆形→直线 | 70 s | 成功，约 14.01 s |
| S4 | 否，承接 S3 | `px4_position` | 直线→圆形 | 70 s | 成功，约 13.96 s |
| S5 | 是 | `ladrc_acceleration` | 8 机圆形 | 45 s | 失败，UAV2/3/7 未稳定 |

S1 的状态快照包含 8/8 新鲜状态，安全分配成功，规划最小三维间距为 2.547 m，命令也已被全部控制节点接收。因此 S1 的失败发生在控制/完成阶段，不是状态缺失或任务分配失败。

S1 超时时实时话题显示 8/8 `is_hover_stable=false`，多架机 LADRC 输出达到水平 `±5 m/s²` 和垂直限幅；高度目标为 5 m 时，实测仍约为 -1.1 至 -1.25 m，典型三维误差为 6 m 以上。

S5 再次冷启动后，45 s 时有 5/8 已稳定，但 UAV2、UAV3、UAV7 未稳定；其中 UAV7 的误差为 `(2.753, -4.719, 6.367) m`。两次同任务失败规模差异很大，说明启动和闭环结果具有明显非确定性。

`px4_position` 对照组表明 8 机通信和执行链条能够完成任务。S2 是一个门限边界问题：45 s 时仅剩 3 架未满足判据，约 3 s 后 8/8 全部为 true。随后 S3、S4 都在期望 12 s 轨迹结束后约 2 s 内完成。

## 5. 问题分级

### P0：LLM 输出清洗与当前模型不兼容

影响：所有自然语言任务在进入调度器前失败，全链路可用率为 0/4。

证据：12/12 调用均无有效 JSON；模型原始响应带 `<think>`，当前清洗使用贪婪对象匹配。

建议验收：对带思考标签、代码块、前后说明和嵌套对象的响应建立固定回归样本；只提取 `</think>` 后的单个完整 JSON，或使用流式/增量 JSON 解码；重试前必须根据失败原因改变恢复策略。

### P0：LADRC 加速度路径不能可靠完成 8 机任务

影响：默认控制模式两次冷启动均失败；一次 8/8 不稳定，另一次 3/8 不稳定。

证据：控制调试话题出现长时间限幅和大误差，而相同下游链路在 `px4_position` 下成功。

建议验收：先做单机阶跃、起飞和定点悬停，再扩展到 2/4/8 机；至少 10 次冷启动全部完成，并统计 RMSE、限幅占比、最小间距和稳定时间，不能只观察单次最终状态。

### P0：飞控启动状态机没有实际确认 ARM/OFFBOARD

状态机在固定延时后直接打印“解锁成功”和“Offboard 模式已激活”，但节点只订阅 `VehicleOdometry`，未订阅 PX4 的武装/导航状态来确认命令结果。此外，进入运行态之前只发布 `OffboardControlMode`，不发布有效 `TrajectorySetpoint`。这会使日志声称成功与 PX4 实际状态脱节，并放大冷启动差异。

建议验收：以 `VehicleStatus`/`VehicleControlMode` 的实际反馈驱动状态迁移；进入 Offboard 前连续发送合法 setpoint；为 arm 和 mode command 增加 ACK、超时、重试和失败态。

### P1：完成门限容易产生边界误报

S2 在 45 s 报错后约 3 s 即 8/8 稳定。项目默认门限是 120 s，但实验覆盖时若使用较短固定值，会把接近完成的任务记为失败。

建议验收：门限应至少包含启动耗时、轨迹时长、预计收敛时间和稳定保持窗口；报告中分别记录“轨迹结束”“首次进入误差带”“持续稳定完成”，不要只保留单一超时布尔值。

### P1：稳定判据为单样本置位

当前实现只要轨迹结束后某一周期满足 `位置误差 < 0.3 m` 且 `速度 < 0.3 m/s` 就把稳定状态置为 true。没有连续保持窗口，可能把瞬时穿越误差带当作稳定。

建议验收：增加连续稳定时长或连续样本数，并在再次越界时明确是否撤销稳定状态。

### P2：仿真启动脚本的无头参数未生效

以 `HEADLESS=1` 启动时脚本仍拉起 `gzclient`。这不是本次任务失败主因，但会增加 8 机批量测试的资源开销和显示环境依赖。

## 6. 框架分层评价

| 层级 | 评价 | 依据 |
|---|---|---|
| 英文指令→Candidate LFS | 不可用 | 0/4 指令成功，12/12 JSON 解码失败 |
| Candidate 校验与策略解析 | 可用 | 手工隔离输入通过 schema 和策略校验 |
| 8 机状态快照 | 可用 | S1/S2/S5 均取得完整新鲜快照 |
| 几何生成与安全分配 | 可用 | 圆形/直线均生成并发布，S1 规划无硬冲突 |
| ROS 2 / XRCE-DDS 通信 | 基本可用 | 8/8 PX4 连接，8/8 调试与状态话题可读 |
| PX4 位置控制执行 | 可用但门限需校准 | 两次连续变换成功，首次冷启动边界超时 |
| LADRC 加速度执行 | 不可靠 | 两次冷启动均失败，结果离散且出现限幅 |
| 完成判定 | 可运行但语义偏弱 | 能结束成功任务，但单样本置位且短门限误报 |
| 可观测性 | 部分可用 | ROS 调试话题有效；缺少一次任务一份自动归档 |

## 7. 建议修复顺序与复测门槛

1. 修复 LLM 响应提取，并用本次 4 条指令做离线和在线回归；目标是 12/12 尝试可得到唯一合法 JSON，正常场景不依赖重试。
2. 修复 ARM/OFFBOARD 握手和预送 setpoint，明确失败态；目标是 10 次 8 机冷启动全部确认 armed + offboard。
3. 单独调试 LADRC 加速度链路，先单机、后扩群；目标是 10 次 8 机圆形任务全部完成，无持续限幅，且稳定判据带连续保持窗口。
4. 把完成门限改为分阶段预算，并记录各阶段时间；目标是冷启动和热启动分别统计，不再用一个固定超时混合判断。
5. 建立自动试验归档：保存英文原始指令、模型原始响应/提取结果、LFS、状态快照、逐周期 `control_tracking_debug`、PX4 状态、完成事件和资源占用。

在以上 P0 修复并通过重复冷启动门槛前，不建议把当前 `main` 用于无人值守 8 机全链路演示。
